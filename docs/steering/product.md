# Product steering — Beer Tracker (Sprint Manager)

## Назначение

Веб-приложение для **планирования спринтов поверх внешнего issue tracker** (**Яндекс Трекер** или **Jira**): визуальное распределение задач по дням, разработчикам и свимлейнам, бэклог, burndown, ретро, метрики и цели спринта; внешний агент планирует через MCP. Провайдер выбирается на организацию — [ISSUE_TRACKERS.md](../ISSUE_TRACKERS.md).

## Пользователи и контекст

- Команды, которые уже ведут задачи в **Яндекс Трекере** или **Jira** и хотят планировать спринт на доске, синхронизируя изменения с трекером.
- Доступ к данным трекера через **пользовательский токен** (Yandex ID OAuth, Atlassian OAuth, Jira PAT / API token). Токен организации для синхронизации хранится зашифрованно в БД, env-fallback нет.

## Ценность (что должно «работать хорошо»)

1. **Планер спринта** — DnD, длительность, позиции, слои строк (авто и ручные), связи задач, заметки на свимлейне, план против факта; виды по исполнителям, по фичам и канбан.
2. **Бэклог** — отбор, фильтры, перенос задач в спринт.
3. **Совместная работа** — realtime, присутствие, ретро, цели спринта.
4. **Агент через MCP** — контекст спринта и предложения плана, которые человек принимает или отклоняет на доске ([SPRINT_CONTEXT.md](../SPRINT_CONTEXT.md)).

## Удалено из продукта

- **Занятость / «По задачам»** (`viewMode === 'occupancy'`) — код удалён; сохранённый режим сбрасывается на свимлейн.
- **Планировщик эпиков / фич** и **квартальное планирование** — экраны и их API удалены.
- **Вкладка «Баги» (SLA-баги)** — вкладка сайдбара, сигналы на карточках, heatmap обращений HD и их API удалены.

Новые фичи и правки — только в планере спринта.

## Вне фокуса продукта (для ясности при фичах)

- Замена внешнего issue tracker как системы учёта задач (приложение **надстраивается** над API провайдера).
- Хранение пользовательских токенов трекера на сервере (токен — в браузере, см. tech steering).

## Качество и риски

- Поломки планера после релизов (перетаскивание карточек, сохранение позиций, сбои из-за параллельных запросов к API) — критичны.
- Расхождение кэша React Query и UI после мутаций — избегать; использовать существующие ключи и патчи (см. ARCHITECTURE.md).
