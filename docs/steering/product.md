# Product steering — Beer Tracker (Sprint Manager)

## Назначение

Веб-приложение для **планирования спринтов поверх внешнего issue tracker** (**Яндекс Трекер** или **Jira**): визуальное распределение задач по дням, разработчикам и свимлейнам, бэклог, burndown и цели спринта. Один провайдер на инстанс — [ISSUE_TRACKERS.md](../ISSUE_TRACKERS.md).

## Пользователи и контекст

- Команды, которые уже ведут задачи в **Яндекс Трекере** или **Jira** и хотят планировать спринт на доске, синхронизируя изменения с трекером.
- Доступ к данным трекера через **пользовательский токен** (OAuth / PAT / API token — основной сценарий); опционально серверный fallback.

## Ценность (что должно «работать хорошо»)

1. **Планер спринта** — DnD, длительность, позиции, связи задач, комментарии на таймлайне; свимлейны по исполнителям и по фичам.
2. **Бэклог** — отбор, фильтры, перенос задач в спринт.

## Deprecated (не развивать)

- **Занятость / «По задачам»** (`viewMode === 'occupancy'`) — скрыта из переключателя видов; сохранённый режим сбрасывается на свимлейн. Код сохранён, **не развивать**.
- **Планировщик эпиков / фич** (`features/feature-planner`, `?page=features`) — экраны отключены от основной навигации.
- **Квартальное планирование** (`features/quarterly-planning-v2`, `?page=quarterly-v2`) — экраны отключены от основной навигации.

Код и API сохранены, но новые фичи и правки — только в планере спринта.

## Вне фокуса продукта (для ясности при фичах)

- Замена внешнего issue tracker как системы учёта задач (приложение **надстраивается** над API провайдера).
- Хранение пользовательских токенов трекера на сервере (токен — в браузере, см. tech steering).

## Качество и риски

- Поломки планера после релизов (перетаскивание карточек, сохранение позиций, сбои из-за параллельных запросов к API) — критичны.
- Расхождение кэша React Query и UI после мутаций — избегать; использовать существующие ключи и патчи (см. ARCHITECTURE.md).
