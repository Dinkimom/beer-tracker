# Бизнес-правила планера

Канон того, **как должен вести себя кор**: раскладка задач на свимлейне, поинты, «сделано», burndown, капасити, жизненный цикл задачи, заметки. Для каждого правила указано, где оно реализовано и каким тестом закреплено.

Пути — от корня репозитория.

## Как пользоваться

- **Меняешь правило — меняешь три вещи в одном PR:** код, тест-закрепитель и строку в этом документе. Правило без теста помечено «нет теста» и считается незакреплённым.
- **Одно правило — одна реализация.** Нужно то же вычисление в другом месте — импортируй функцию из колонки «Где», не пиши свою. Почти все баги кора последних месяцев — расхождение двух копий одного правила.
- Чистые правила живут в `lib/` (или `features/*/utils/`) и тестируются без рендера. Правило внутри хука или MobX-стора — кандидат на вынос.
- Ревью PR, который трогает кор: «какое правило отсюда он меняет и обновлены ли тест и строка?».
- [Известные расхождения и открытые вопросы](#известные-расхождения-и-открытые-вопросы) — долг: каждый пункт либо чинится, либо превращается в правило с явным решением.

Обозначения тестов: имя файла рядом с реализацией (`*.test.ts`).

## 9. «Задача сделана» — единый канон

**Решение:** «сделано» определяет **трекер**, а не организация:

- **Yandex Tracker** — статус с типом «завершено» (`done`) **и** заполненная резолюция.

## Известные расхождения и открытые вопросы

Каждый пункт — либо баг к починке, либо решение, которое нужно принять и записать правилом выше.

**«Сделано» ещё не единое:**

- Отдельные проверки «завершённости» вне канона, по своим причинам: выбор перехода для закрытия просроченной задачи (`features/swimlane/utils/closeOverdueAndCreateNext.ts`), конец полосы факта на свимлейне (`features/swimlane/utils/in-progress-fact/factClosingStatus.ts`), план-факт и категория статуса для MCP-агента (`lib/sprints/sprintContextPlanVsActual.ts`, `lib/mcp/resolveMcpIssueStatusCategory.ts`). Агент может видеть «сделано» иначе, чем UI.
- Без доступа к трекеру (нет токена, сбой) справочник статусов пуст: текущие задачи оцениваются по своему типу статуса, а история (burndown, ретро) не видит закрытий.

**Согласованность данных:**

- Перенос строки фичи не переносит локальные (несохранённые) черновики задач.
- Перенос одной заметки сбрасывает её в день 0 / часть 0, перенос фичи сохраняет позицию.

**Провайдеры:**

- Jira-история маппит только поля `status`, `Story Points`, `Test Points`: кастомные/локализованные поля оценки и поле Sprint не распознаются (переоценка и scope change в burndown Jira не видны). Ключ статуса Jira берётся из имени — зависит от языка.
- Yandex и Jira по-разному снимают задачу со спринта (K1/K2).

**Порядок задач (K7):**

- Yandex: ранг из API не маппится в `rank` — порядок как в ответе поиска. Если у Yandex есть ранг задач доски/спринта, его нужно положить в `rank`, и K7 заработает без других правок.
- Авторасстановка всего спринта сортирует по приоритету и размеру, а не по рангу трекера. Под K7 не подходит — решить, нужен ли ранг и там.
- `occupancy_task_order` (наследие удалённой «Занятости») ещё переставляет задачи в `/api/tracker` поверх ранга для старых спринтов, где строка осталась. Новые строки никто не пишет — кандидат на удаление.
- Снимки PG, записанные до появления `rank`, без ранга: порядок исправится после фонового обновления из трекера или пересинхронизации.

**Праздники (M10):**

- Автодобавление (M6) и размещение QA кнопкой «+QA» праздники не учитывают. Отсутствия (отпуск, больничный) не учитывает ни одна расстановка.

**Прочее:**

- Капасити в MCP учитывает праздники и занятость, клиентский свимлейн сопоставляет события занятости по `memberId` без нормализации префикса `staff:`.
- «Скрывать факт в дни занятости» (bd60a16d) удалено в e56810eb вместе с редизайном дорожек факта — намеренно или регрессия, не решено.
- Заметки: отклонение всех черновиков (`deleteAllPendingSprintComments`) удаляет жёстко и не чистит связи на сервере (клиент удаляет их по одной). Фото и схемы не чистятся из S3 после удаления.
- Схема БД: нет учёта применённых миграций, часть колонок создаётся только кодом — см. [DATABASE.md](./DATABASE.md#известные-проблемы).
