# Руководство по тестированию для агентов (MCP)

## Обзор проекта

**Beer Tracker** — веб-приложение для планирования спринтов по свимлейнам поверх **Яндекс Трекера** или **Jira**. Задачи раскладываются по исполнителям и дням спринта (10 рабочих дней, день — 3 ячейки: `WORKING_DAYS`, `PARTS_PER_DAY` в [`constants/index.ts`](../constants/index.ts)). Провайдер: [ISSUE_TRACKERS.md](./ISSUE_TRACKERS.md).

### Технологический стек

- **Frontend**: Next.js 16, React 19, TypeScript
- **Backend**: Next.js API Routes
- **База данных**: PostgreSQL (позиции задач, цели спринта, доска ретро, снимки задач `issue_snapshots`)
- **Внешние API**: Issue tracker API — Yandex Tracker **или** Jira (мутации, спринты, доски)
- **UI**: Tailwind CSS, Radix UI, dnd-kit (drag-and-drop)

## Где тестировать

| Контур | Адрес | Когда |
|--------|-------|-------|
| Демо на фикстурах | `/demo/planner` | UI планера без логина и трекера. Данные — [`lib/demo/`](../lib/demo/), часы зафиксированы. Состояние живёт в памяти вкладки: перезагрузка страницы возвращает фикстуру. |
| Боевой планер | `/planner/:boardId/sprint/:sprintId?tab=…` | Всё, что пишет в трекер или PostgreSQL: статусы, оценки, перенос в спринт, сохранение позиций после перезагрузки. Нужен логин и подключённый трекер. |

На `/demo/planner` нет аватара и колокольчика уведомлений в шапке, люди на доске — персонажи фикстуры, демо-пользователь не админ (цели спринта не редактирует). Кейсы с контуром `демо` проходят там целиком; `боевой` — только на боевом контуре.

## Архитектура UI

### Страницы

1. **Выбор доски** (`/select-board`) — список досок организации из трекера. После выбора — переход на `/planner/:boardId/sprint/:sprintId?page=sprints&tab=board` (активный спринт, иначе первый в списке).
2. **Планер** (`/planner/:boardId/sprint/:sprintId`) — рабочая область. Вкладки в шапке (`SprintTab` в [`components/PageHeader.tsx`](../components/PageHeader.tsx), query `?tab=`):
   - **Бэклог** (`backlog`) — [`features/backlog/components/BacklogPage.tsx`](../features/backlog/components/BacklogPage.tsx)
   - **Доска** (`board`, по умолчанию) — свимлейн / канбан, [`features/sprint/components/SprintPlanner/SprintPlannerView.tsx`](../features/sprint/components/SprintPlanner/SprintPlannerView.tsx)
   - **Роадмап** (`quarter`) — квартальный план, [`features/quarterly-plan/`](../features/quarterly-plan/)
   - **Диаграмма сгорания** (`burndown`) — [`features/burndown/components/BurndownChart.tsx`](../features/burndown/components/BurndownChart.tsx)
   - **Ретро** (`retro`) — [`features/retro/components/RetroPage.tsx`](../features/retro/components/RetroPage.tsx)
   - **Метрики** (`metrics`) — [`features/sprint-metrics/components/SprintMetricsPage.tsx`](../features/sprint-metrics/components/SprintMetricsPage.tsx)
3. **Админка** (`/admin/*`) — вне этого руководства.

### Доска (вкладка `board`)

- Панель управления сверху: селектор спринта, отмена/повтор плана, перезагрузка задач, режим отображения (**По исполнителям** / **По фичам** / **Канбан**), кнопка сайдбара.
- Свимлейн ([`features/swimlane/`](../features/swimlane/), карточка — [`features/task/components/TaskBar/`](../features/task/components/TaskBar/)): строка на исполнителя, колонки — дни спринта.
- Правый клик по карточке — контекстное меню ([`features/context-menu/components/ContextMenu.tsx`](../features/context-menu/components/ContextMenu.tsx)): статус, исполнитель, оценка, родитель, перенос в спринт, «Удалить из плана», «Убрать из спринта», «Информация о задаче».

### Сайдбар доски

Вкладки ([`features/sidebar/components/SidebarTabContent.tsx`](../features/sidebar/components/SidebarTabContent.tsx)), порядок и видимость настраиваются:

- **Задачи** — незапланированные задачи спринта, поиск, фильтр по статусу, группировка, «Автоплан», «Вернуть все»
- **Бэклог** — задачи вне спринта
- **Спринт** — цели Delivery / Discovery, запуск и завершение спринта
- **Дейли**, **Метрики**

## Автоматический регресс

Playwright, конфиг — [`playwright.config.ts`](../playwright.config.ts), спеки — [`e2e/`](../e2e/). Всё идёт на `/demo/planner` против уже запущенного dev-сервера.

| Команда | Что делает |
|---------|------------|
| `pnpm e2e` | Функциональные спеки `e2e/functional` на хосте |
| `pnpm e2e:visual` | Визуальные спеки `e2e/visual` в Linux-образе Playwright (Docker): каждый экран шапки в светлой и тёмной теме против эталонов `e2e/visual/__screenshots__` |
| `pnpm e2e:visual:update` | Переснять эталоны (только после задуманного изменения вида) |
| `pnpm e2e:audit` | Аудит интерфейса в Linux-образе: детекторы проблем по каждому экрану шапки в обеих темах; падает только на новых находках |
| `pnpm e2e:audit:update` | Переписать список известных проблем `e2e/audit/known/` (после исправления или осознанного принятия) |
| `pnpm e2e:tour` | Тур состояний для разбора глазами (меню, окна, панели, пустые результаты, узкое окно): кадры и находки детекторов в `e2e/.results/tour/`. Не проверка, в CI не идёт — материал для скилла `ui-audit` |
| `pnpm e2e:report` | HTML-отчёт последнего прогона с expected/actual/diff |
| `pnpm e2e:affected` | Какие кейсы задевает текущий diff и какие изменённые UI-файлы не покрыты ни одним кейсом |
| `pnpm check:e2e-cases` | Сверка каталога с кодом и спеками (входит в `pnpm test`) |

- **Фикстура** [`e2e/fixtures.ts`](../e2e/fixtures.ts): английский UI, тема, пройденный онбординг; тест падает, если браузер написал `console.error` или бросил исключение. Подписи — из словаря `en`, локаторы — по роли и доступному имени.
- **Эталоны только из Linux-образа.** Шрифты и сглаживание macOS дают другие пиксели, поэтому вне Linux визуальные спеки пропускаются, а `pnpm e2e:visual` запускает их в `mcr.microsoft.com/playwright` той же версии, что `@playwright/test`. Допуск — ноль отличающихся пикселей: прогоны в образе детерминированы, а любой допуск по площади прятал сдвиг подписи вкладки.
- **CI** — job `e2e` в [`.github/workflows/ci.yml`](../.github/workflows/ci.yml): тот же образ, свой dev-сервер (демо работает без БД и трекера), функциональные и визуальные спеки. При падении отчёт и диффы — в артефакте `e2e-report`.
- **Аудит интерфейса** ([`e2e/audit/`](../e2e/audit/)) ищет не отличия от эталона, а проблемы, которые плохи сами по себе: нарушения WCAG 2.1 A/AA (axe-core: контраст, имена контролов, вложенные интерактивные элементы, ARIA), текст, обрезанный без многоточия и подсказки, контролы, перекрытые другими элементами, кнопки без курсора-руки и без отклика на наведение (наводится по-настоящему), выключенные кнопки, которые выглядят активными. Сеть: ответы 4xx/5xx роняют любой тест через фикстуру. Известные проблемы — `e2e/audit/known/<экран>-<тема>.json`; новая находка или исчезнувшая (исправили, а список не обновили) роняют прогон. Принять находку в список можно только с объяснением в коммите; по умолчанию — чинить.
- **Агентский аудит** — скилл [`ui-audit`](../.claude/skills/ui-audit/SKILL.md): тур состояний → разбор каждого кадра по чек-листу (единообразие, раскладка, текст, состояния, тёмная тема, аффорданс, обратная связь, шаги) → отсев известного → серьёзность → строки в `CLEANUP_BACKLOG.md`. Детекторы отвечают за объективное, агент — за то, что видно только глазами.
- **Результат для агента** — `e2e/.results/results.json`; артефакты падений (скриншот, `error-context.md` с деревом страницы, trace, для визуальных — `*-expected.png`, `*-actual.png`, `*-diff.png`) — `e2e/.results/artifacts/`.

## Постоянный процесс: фича → кейсы → тесты

Каталог и автотесты живут вместе с продуктом. Задача, которая меняет видимое пользователю поведение, не считается сделанной, пока не пройден цикл (скилл [`regress`](../.claude/skills/regress/SKILL.md) проводит его целиком):

1. **Что задето** — `pnpm e2e:affected`. Задетые кейсы пересмотреть; изменённые UI-файлы без кейса — новое поведение без описания.
2. **Каталог** — изменить «Шаги»/«Ожидаемо» задетых кейсов, завести кейс на новое поведение, удалить кейс убранного. Номера не переиспользуются.
3. **Автотесты** — для демо-кейсов написать или поправить тест (название начинается с `TC-NNN`), в «Автотест» кейса — путь к спеке. Новый экран шапки — маркер в `SCREEN_MARKERS`, визуальная спека подхватит его сама.
4. **Прогон** — `pnpm e2e`, `pnpm e2e:visual`. Каждое падение разобрать: регресс (чинить код), задуманное изменение (каталог, тест, эталон), хрупкий тест (чинить тест). Эталоны пересъёмки посмотреть глазами.
5. **Сверка** — `pnpm test` включает `check:e2e-cases` и ломается, если путь из «Код» исчез, спека ссылается на несуществующий кейс или кейс указывает автотест, которого нет.

Почему это держится: путь в «Код», которого больше нет, ломает CI. Спека без кейса и кейс без спеки тоже ломают CI. А `e2e:affected` при каждой правке показывает, какие кейсы перечитать.

## Критерии успешного тестирования

### Функциональные

- Задачи перетаскиваются между сайдбаром, исполнителями и днями
- Позиции, цели и ретро сохраняются после перезагрузки (боевой контур)
- Статусы, оценки и перенос в спринт синхронизируются с трекером
- Бэклог показывает задачи вне спринтов, перенос в обе стороны работает

### Нефункциональные

- Перетаскивание без заметных лагов
- Ошибки показываются пользователю (тосты), консоль браузера без необработанных ошибок

## Ручная проверка и боевой контур

1. **Сервер**: уже запущенный dev-сервер (`pnpm docker:dev` → `http://localhost:3000`) или `pnpm dev`. Второй не поднимать. Установка и `.env` — [INSTALL.md](./INSTALL.md).
2. **Демо-кейсы** сначала через автотесты (выше). Руками — то, что исследуется за пределами скриптов: одноразовый скрипт Playwright или браузерный MCP, скриншот, проверка консоли.
3. **Боевой контур** (кейсы `боевой`): логин, подключённый трекер (Yandex Tracker или Jira), доступная PostgreSQL. Агент гоняет его только по просьбе пользователя — кейсы пишут в трекер и БД. Дополнительно проверить, что изменения дошли до трекера и пережили перезагрузку.

### Отчёт

```markdown
## Регресс: <ветка или задача>
Задетые кейсы: TC-…, TC-… · новые: TC-… · удалённые: TC-…
Функциональные: N ✓ / M ✗ · визуальные: N ✓ / M ✗ (эталоны пересняты: какие и почему)
Падения:
- TC-081 ✗ регресс — что сломано, где починено
Исследование: что прошёл руками, что нашёл
Не запускалось: что и почему
```
