# Встроенный трекер otorva

Собственный трекер задач на Rust ([`services/otorva`](../services/otorva/)) — третий провайдер beer-tracker рядом с Яндекс Трекером и Jira и вариант «Встроенный трекер» на онбординге. Второе назначение — регресс: сквозные сценарии на настоящем трекере, а не только на фикстурах демо.

## Решения

| Вопрос | Решение |
|---|---|
| Где код | Монорепа: `services/otorva`, перенесён из `rusticapps/otorva` с историей (git subtree, 2026-11-22). Публичный, под лицензией репозитория |
| Где логика трекера | В otorva. Доски, спринты, ключи, оценки, фильтры и журнал изменений — Rust и интеграционные тесты otorva; провайдер в beer-tracker тонкий, как для Яндекса и Jira |
| Вход | Email и пароль otorva: онбординг создаёт первого пользователя, вход в beer-tracker — по email и паролю otorva, JWT — токен трекера (вместо OAuth). Новых людей добавляет админ |
| Поставка | Свой образ: Containerfile otorva (stage `api` и `migrator`). В compose — сервисы `otorva-migrate` и `otorva`, своя база `otorva` на общем PostgreSQL |

## Контракт провайдера и otorva

Контракт — `IssueTrackerProviderClient` (`lib/issueTrackerProvider/types.ts`, около 50 методов); полный каталог — `lib/issueTrackerProvider/contracts/issueTrackerProviderClientMethodCatalog.ts`.

| Нужно планеру | В otorva на 2026-11-22 | Этап |
|---|---|---|
| Пользователь и токен (`getCurrentUser`, `/myself`, первый админ) | JWT по email и паролю, `/auth/me`; регистрация выключена (`ALLOW_REGISTRATION`) | 1, 2 |
| Задачи: получить, создать, обновить, переходы, связи | Есть; id — UUID, ключей вида `KEY-12` нет | 1 |
| Очереди (`listQueues`, ключ очереди, воркфлоу очереди) | Нет; воркфлоу привязан к типу задачи | 1 |
| Выборки: по доске, очереди, обновлённые за период, поиск | Только `limit/offset` (до 200) без фильтров | 1 |
| Доски и спринты: список, статус, цель, состав | Нет | 1 |
| Поля: оценки SP/TP, сроки, родитель | Нет; произвольное — `extra_fields` (JSONB) | 1 |
| История изменений (`getIssuesChangelogBatch`, вкладка «История», сгорание) | Нет | 1, 3 |
| Комментарии, чек-листы | Нет | позже, capability выключена |

## Этапы

0. **Монорепа и сборка** — сделано: `services/otorva`, compose-профиль `otorva`, job `otorva` в CI (`cargo test` с PostgreSQL).
1. **Модель планирования в otorva**: очереди с ключом и порядковыми ключами задач; поля оценок, сроков и родителя; доски и спринты с составом; фильтры списка (очередь, спринт, исполнитель, статус, родитель, обновлено с/по, текст); журнал изменений задачи (поле, было, стало, автор, время) в транзакции правки; создание пользователей админом.
2. **Провайдер `otorva` в beer-tracker**: вид провайдера и хранимый провайдер, клиент (частичная реализация по образцу Jira: неподдержанное — `UnsupportedIssueTrackerOperationError`), capabilities, вход по email и паролю, вариант на онбординге и в админке, i18n ru/en, контрактные тесты. Сервис `otorva` — стандартный в compose (без профиля).
3. **Синк и история**: синк на `listIssuesUpdatedInRange` и `listIssuesForQueue`, снимки, журнал otorva → `issue_changelog_events`, вкладка «История» и диаграмма сгорания.
4. **Регресс на локальном трекере**: сид из фикстур демо (`lib/demo/`), контур «локальный трекер» в [`TEST_CASES.md`](./TEST_CASES.md), e2e по сквозным сценариям, job в CI.

## Запуск

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile otorva up -d otorva
curl http://127.0.0.1:8090/health
```

В dev-оверрайде секрет JWT — локальная заглушка; в обычном compose нужен `OTORVA_JWT_SECRET` (≥32 байт, `openssl rand -hex 32`).
