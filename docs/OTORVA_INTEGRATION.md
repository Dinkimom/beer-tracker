# Встроенный трекер otorva

Собственный трекер задач на Rust ([`rusticapps/otorva`](https://github.com/rusticapps/otorva)) — третий провайдер beer-tracker рядом с Яндекс Трекером и Jira и вариант «Встроенный трекер» на онбординге. Второе назначение — регресс: сквозные сценарии на настоящем трекере, а не только на фикстурах демо.

## Решения

| Вопрос | Решение |
|---|---|
| Где код | Отдельный приватный репозиторий `rusticapps/otorva`. Доработки этапа 1 делались в монорепе и влиты PR #1 (2026-11-22); в beer-tracker — только обвязка: провайдер, compose, стенд |
| Где логика трекера | В otorva. Доски, спринты, ключи, оценки, фильтры и журнал изменений — Rust и интеграционные тесты otorva; провайдер в beer-tracker тонкий, как для Яндекса и Jira |
| Вход | Email и пароль otorva: онбординг создаёт первого пользователя, вход в beer-tracker — по email и паролю otorva, JWT — токен трекера (вместо OAuth). Новых людей добавляет админ |
| Поставка | Свой образ: Containerfile otorva (stage `api` и `migrator`) из клона `../otorva` или `OTORVA_SOURCE`. В compose — сервисы `otorva-migrate` и `otorva`, своя база `otorva` на общем PostgreSQL; в CI клон берётся токеном `OTORVA_REPO_TOKEN` |

## Контракт провайдера и otorva

Контракт — `IssueTrackerProviderClient` (`lib/issueTrackerProvider/types.ts`, около 50 методов); полный каталог — `lib/issueTrackerProvider/contracts/issueTrackerProviderClientMethodCatalog.ts`.

| Нужно планеру | В otorva на 2026-11-22 | Этап |
|---|---|---|
| Пользователь и токен (`getCurrentUser`, `/myself`, первый админ) | JWT по email и паролю, `/auth/me`, админы, первый админ по секрету установки | 2 |
| Задачи: получить, создать, обновить, переходы, связи | Есть; ключ `KEY-12` по очереди | — |
| Очереди (`listQueues`, ключ очереди, воркфлоу очереди) | Очереди есть; воркфлоу привязан к типу задачи, не к очереди | 1 |
| Выборки: по доске, очереди, обновлённые за период, поиск | Есть: фильтры `GET /tasks`, `X-Total-Count`, порядок для синка | — |
| Доски и спринты: список, статус, цель, состав | Есть: целочисленные id, `version`, задача в нескольких спринтах | — |
| Поля: оценки SP/TP, сроки, родитель | Есть: `story_points`, `test_points`, `start_date`, `end_date`, `parent_id` | — |
| История изменений (`getIssuesChangelogBatch`, вкладка «История», сгорание) | Журнал `task_events`, пачкой по ключам | 3 |
| Комментарии, чек-листы | Нет | позже, capability выключена |

## Этапы

0. **Сборка** — сделано: compose-профиль `otorva` из клона `rusticapps/otorva`; тесты трекера — в его репозитории.
1. **Модель планирования в otorva** — сделано: ~~очереди с ключом и порядковыми ключами задач~~ (сделано: `queues`, ключ `KEY-12`, `GET /tasks/by-key/{key}`); ~~поля оценок, сроков и родителя~~ (сделано); ~~доски и спринты с составом~~ (сделано); ~~фильтры списка (очередь, спринт, исполнитель, статус, родитель, обновлено с/по, текст)~~ (сделано, плюс `keys`, `sort=updated_asc`, `X-Total-Count`); ~~журнал изменений задачи (поле, было, стало, автор, время) в транзакции правки~~ (сделано: `task_events`); ~~создание пользователей админом~~ (сделано: `is_admin`, `GET /auth/setup-state`, `POST /auth/bootstrap` по `OTORVA_BOOTSTRAP_TOKEN`).
2. **Провайдер `otorva` в beer-tracker** — сделано, кроме админки: вид провайдера и хранимый провайдер, клиент (частичная реализация по образцу Jira: неподдержанное — `UnsupportedIssueTrackerOperationError`), capabilities, вход по email и паролю, вариант на онбординге и в админке, i18n ru/en, контрактные тесты. Сервис `otorva` — стандартный в compose (без профиля).
3. **Синк и история** — сделано (живой прогон синка — на стенде этапа 4): синк на `listIssuesUpdatedInRange` и `listIssuesForQueue`, снимки, журнал otorva → `issue_changelog_events`, вкладка «История» и диаграмма сгорания.
4. **Регресс на локальном трекере** — сделано: стенд `pnpm e2e:stand` (пустые база и otorva, сид из фикстур демо), раздел «Стенд регресса» в [`TEST_CASES.md`](./TEST_CASES.md) (TC-134…140), спеки `e2e/stand/`, job `e2e-stand` в CI. Как устроен — [AGENT_TESTING_GUIDE.md](./AGENT_TESTING_GUIDE.md#стенд-регресса-встроенный-трекер).

### Что сделано на этапе 2

- Вид провайдера `otorva`, клиент на общем `partialProviderClient`: чтение (задачи, выборки, доски с колонками, спринты, статусы по категории otorva, люди, очереди, переходы, связи, журнал как changelog) и запись (создание, правка, переходы, членство в спринтах, спринты, связи `relates`). Комментариев и чек-листов нет — 422.
- Без веб-интерфейса: ключи задач текстом, «скопировать ссылку» скрыто (`supportsIssueWebLinks`); демо `?tracker=otorva`, TC-133.
- Вход: `POST /api/auth/otorva/session` — email и пароль → JWT otorva; онбординг на пустом otorva создаёт первого админа по серверному `OTORVA_BOOTSTRAP_TOKEN`. JWT дальше идёт по общим путям как токен трекера; сырой `/myself` для otorva уходит в `/auth/me`. Подключение организации требует админа otorva.
- `pnpm docker:dev` поднимает otorva; в обычном compose — профиль `otorva` и секреты `OTORVA_*` (env.example).

### Что сделано на этапе 3

- Снимок задачи (`issue_snapshots`) — в форме Яндекса из полей провайдера, с меткой `otorva` в конверте; сырой DTO otorva в снимок не попадает (терял бы статус и спринты). Полный цикл «задача → снимок → задача» закреплён тестом.
- Журнал otorva (`GET /task-events?keys=`) → changelog в форме Яндекса: поля `assignee`, `deadline`, `sprint`, `start`, `status`, `storyPoints`, `testPoints` — их читает `issue_field_events` для вкладки «История»; статус узнаётся по ключу из справочника.
- Диаграмма сгорания — `getBurndownIssuesForKeys` из журнала, по общему построителю.

### Что нашёл стенд на этапе 4

- Планер на каждом открытии доски просил экраны переходов (`getQueueWorkflowScreens`) — у otorva 422 и ошибка в консоли; теперь пустой ответ, как у Jira.
- «Перенести в спринт» добавлял задачу в спринт otorva, не снимая со старого: задача копилась в спринтах. Теперь как у Яндекса — спринты той же доски заменяются.
- Мелочи интерфейса — в [CLEANUP_BACKLOG.md](./CLEANUP_BACKLOG.md#встроенный-трекер-стенд-pnpm-e2estand).

### Открытые вопросы

- **Срок сессии.** Секрет организации для синка — JWT админа; в compose срок 30 дней (`OTORVA_JWT_EXP_HOURS`). Нужны долгоживущие API-токены в otorva (выпуск и отзыв админом).
- **Админка «Трекер».** Для otorva форма подключения пока предлагает вставить токен сессии; нужна форма «войти как администратор» (email и пароль → токен) для переподключения.
- **Лимит попыток входа** считает otorva по адресу сервера планера — общий на всех пользователей (30 в минуту). Для перебора это правильно; если станет тесно — лимит на стороне планера по IP пользователя.

## Запуск

```bash
git clone git@github.com:rusticapps/otorva.git ../otorva   # один раз
docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile otorva up -d otorva
curl http://127.0.0.1:8090/health
```

В dev-оверрайде секрет JWT — локальная заглушка; в обычном compose нужен `OTORVA_JWT_SECRET` (≥32 байт, `openssl rand -hex 32`).
