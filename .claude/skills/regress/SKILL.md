# Регресс

Аргументы: `$ARGUMENTS`. Пусто или `affected` — работа по текущему diff (основной режим, в конце каждой фичи).
`full` — весь набор и весь каталог. `case TC-NNN` — написать или починить автотест для кейсов.
`visual-update` — только пересъёмка эталонов после намеренного изменения вида.

Опора:

- [`docs/TEST_CASES.md`](../../../docs/TEST_CASES.md) — каталог кейсов, источник правды: формат, контур, «Код», автотест;
- [`docs/AGENT_TESTING_GUIDE.md`](../../../docs/AGENT_TESTING_GUIDE.md) — где и как гонять, боевой контур;
- [`e2e/fixtures.ts`](../../../e2e/fixtures.ts) — фикстура демо, страж консоли, маркеры экранов;
- `pnpm check:e2e-cases` — сверка каталога с кодом и спеками (входит в `pnpm test`, ломает CI).

Dev-сервер должен отвечать: `curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/demo/planner` → `200`.
Если нет — попросить пользователя запустить (`pnpm docker:dev` или `pnpm dev`). Второй сервер не запускать.

## 1. Что задето

```bash
pnpm e2e:affected            # --base <ref>, если ветка не от master
```

Выводит кейсы, чей «Код» задет diff, и изменённые UI-файлы без кейса. Дальше по каждому:

| Что видно | Что делать |
|---|---|
| Кейс задет, поведение по шагам то же | Ничего в каталоге; автотест прогнать в шаге 3 |
| Кейс задет, поведение изменилось | Переписать «Шаги»/«Ожидаемо» под новый продукт, затем спеку |
| Поведение убрано | Удалить кейс (номер не переиспользуется) и его тест |
| UI-файл без кейса, новое поведение для пользователя | Новый кейс в нужном разделе, следующий свободный номер |
| UI-файл без кейса, поведение уже описано другим кейсом | Дописать путь в «Код» того кейса |
| UI-файл без кейса, пользователю не видно (рефакторинг, стили без смены вида) | Ничего; сказать в отчёте |

Новый кейс — с точки зрения пользователя: шаги в терминах интерфейса, ожидание проверяемое. «Код» — папка
или файлы, которые реализуют поведение, не вся `features/`. Демо-кейс без автотеста — только с причиной
(«нет — очередь автоматизации», «нет — нет данных в фикстуре»). Не уверен, что поведение задумано, — спросить
пользователя, не записывать догадку в каталог как ожидаемое.

## 2. Автотесты из кейсов

Для каждого нового или изменённого демо-кейса — тест в `e2e/functional/<тема>.spec.ts`, название начинается
с номера: `test('TC-081: …')`, несколько близких кейсов в одном тесте — `TC-040/041: …`. В «Автотест» кейса —
путь к спеке. Правила:

- Импорт `test`, `expect`, `en`, `openDemoPlanner`, `openSprintTab` из `../fixtures`. Каждый тест начинает с
  `openDemoPlanner(page)`; состояние демо свежее в каждом тесте.
- Локаторы — по роли и доступному имени: `getByRole('button', { name: en.retro.addCard })`. Подписи — из
  словаря `en`, не строками. Данные фикстуры — импортом из `lib/demo/` (`DEMO_DEV_DISPLAY`), где есть константа;
  иначе текстом фикстуры.
- Нет доступного имени у контрола — это дыра доступности: добавить `aria-label` в компонент (в том же
  изменении), а не `data-testid` и не CSS-селектор.
- Никаких `waitForTimeout`: ждать проверяемое состояние через `expect(...)`.
- Шаги сценария — `test.step`, чтобы в отчёте было видно, где сломалось.
- Поведение не воспроизводится на фикстурах — сначала данные в `lib/demo/` (с unit-тестом, если там логика),
  потом тест. Демо-роутер отвечает не как боевой API — это баг демо, чинить в `lib/demo/`.
- Новый экран или вкладка шапки — маркер в `SCREEN_MARKERS` (`e2e/fixtures.ts`). Визуальная спека подхватит его
  сама, эталоны снять в шаге 4.

Проверить, что тест ловит регресс: временно сломать ожидаемое поведение (или ожидание в тесте), увидеть красный,
вернуть. Тест, который не может упасть, не нужен.

## 3. Прогон

```bash
pnpm e2e                                   # функциональные, против dev-сервера хоста
pnpm e2e --grep "TC-081"                   # один кейс
pnpm e2e:visual                            # визуальные — в Linux-образе Playwright (Docker)
pnpm e2e:audit                             # аудит интерфейса — там же
```

Итог в `e2e/.results/results.json`, артефакты падений (скриншот, `error-context.md` с aria-снапшотом, trace) —
в `e2e/.results/artifacts/`. Отчёт для человека: `pnpm e2e:report`.

## 4. Разбор каждого падения

Не перезапускать до зелёного и не поднимать пороги. Для каждого красного теста определить класс:

**Функциональный.** Прочитать ошибку и `error-context.md` (там дерево страницы в момент падения).

| Класс | Признак | Действие |
|---|---|---|
| Регресс | Поведение расходится с «Ожидаемо» кейса, и изменение этого не задумывало | Чинить код, не тест |
| Намеренное изменение | Diff задумал новое поведение | Каталог (шаг 1), потом тест |
| Хрупкий тест | Локатор по вёрстке, гонка, зависимость от порядка | Переписать по правилам шага 2; `--repeat-each=5` зелёный |
| Ошибки консоли | Фикстура упала на `console.error` / `pageerror` | Это баг приложения: чинить причину, не глушить |

**Визуальный.** Read всех трёх картинок из `e2e/.results/artifacts/<тест>/`: `*-expected.png`, `*-actual.png`,
`*-diff.png`. Описать словами, что поменялось и где.

- Изменение следует из задачи (новая кнопка, другой отступ, который и меняли) — намеренное. Пересъёмка:
  `pnpm e2e:visual:update`, затем Read новых эталонов в `e2e/visual/__screenshots__/` светлой и тёмной темы.
  Эталон фиксирует то, что ты посмотрел и счёл правильным: обрезанный текст, наезды, тосты, спиннеры в кадре —
  повод чинить, а не принимать.
- Изменение не следует из задачи (сдвинулся соседний экран, поменялся цвет в тёмной теме) — регресс, чинить.
- Шум (единичные пиксели сглаживания, курсор, анимация) — нестабильный кадр: убрать источник в спеке
  (наведение, анимация, текущее время), а не поднимать `maxDiffPixelRatio`.

**Аудит** (`pnpm e2e:audit`). Новая находка — проблема интерфейса, которую принесло изменение: чинить
(подпись контролу, контраст токеном из `app/globals.css`, hover/cursor по образцу `HeaderIconButton`).
Ложное срабатывание детектора — чинить детектор в `e2e/audit/detectors.ts`, а не список. Принять находку в
`e2e/audit/known/` (`pnpm e2e:audit:update`) можно только осознанно, с причиной в сообщении коммита.
Исчезнувшая находка — кто-то починил: обновить список тем же `pnpm e2e:audit:update`.

Пересъёмку эталонов без задуманного изменения вида не делать. Обновлённые эталоны — в том же коммите, что и
изменение, с одной строкой в сообщении коммита: какие экраны и почему.

## 5. Исследование за пределами скриптов

Скрипты проверяют записанное. После зелёного прогона пройти изменённый сценарий руками на `/demo/planner`:
одноразовый скрипт Playwright в scratchpad (как в `e2e/fixtures.ts`: язык, тема, онбординг), клики по
изменённому потоку и соседним — пустые состояния, длинные названия, отмена/Esc, повторное действие, обе темы.
Скриншоты — Read. Нашёл и починил — добавить кейс и тест, чтобы не вернулось. Нашёл и не чинишь — строка в
[`docs/CLEANUP_BACKLOG.md`](../../../docs/CLEANUP_BACKLOG.md).

Боевой контур (кейсы `боевой`) агент гоняет только по просьбе пользователя: пишет в трекер и PostgreSQL.

## 6. Отчёт

```markdown
## Регресс: <ветка или задача>
Задетые кейсы: TC-…, TC-… · новые: TC-… · удалённые: TC-…
Функциональные: N ✓ / M ✗ · визуальные: N ✓ / M ✗ (эталоны пересняты: board-light, board-dark — почему)
Падения:
- TC-081 ✗ регресс — что сломано, где починено
Исследование: что прошёл руками, что нашёл
Не запускалось: что и почему (нет Docker, нет сервера)
```

Не коммитить без просьбы. `pnpm check:e2e-cases` и `pnpm lint` — зелёные до того, как говорить «готово».
